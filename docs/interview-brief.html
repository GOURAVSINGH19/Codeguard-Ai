1 · The pitch

Say this first

30 seconds

“CodeGuard AI reviews GitHub pull requests. GitHub sends a webhook, my Next.js app verifies it, saves it to Postgres and puts it on Kafka. Workers then run a staged review: they work out which files depend on the change using an import graph, pull related code with vector search, run quality, security and testing reviewers in parallel, and use a second model to check every finding. The result is inline comments and a Check Run that can block the merge. Most of my effort went into making it fail safely.”

2 minutes (add these after the 30 seconds)

“The webhook handler only verifies, saves and publishes, because GitHub waits about ten seconds and a review takes minutes. Saving before publishing is the transactional outbox pattern: if Kafka is down, a sweeper publishes the row later. That means a message can arrive twice, so every consumer is idempotent. The review worker claims the review with a unique index on PR, commit and requester.”

“For context, the worker downloads a read-only snapshot of the exact commit. Tree-sitter extracts imports, and a BFS over reverse edges finds the blast radius, so a one-line change to a shared utility gets more attention than 200 lines in a test. Code chunks are embedded into pgvector so the reviewer can cite real files.”

“Every model answer is parsed with Zod and gets one repair attempt. The verifier marks each finding confirmed, uncertain or rejected, and only confirmed findings can fail the check. I built an eval harness with planted bugs: the verifier raised precision from 47% to 80% with recall at 100%.”

  2. Dedupe and save. github_delivery_id is UNIQUE. A redelivery of a failed event is allowed to run again.GitHub can deliver twice and doesn't retry on its own.packages/db/schema/webhook-events.ts
  3. Publish to Kafka, key owner/repo#number, then reply 200.Same key, same partition, so one PR's pushes stay in order.packages/kafka/src/topics.ts · client.ts
  4. Route. decideRoute() is a pure function returning review, index, index-full or ignored.Pure, so every branch is unit-tested without a database.apps/workers/src/jobs/webhookProcessor.ts
  5. Consume safely. Bad JSON or schema goes straight to DLQ. Errors retry 3 times (2 s, 4 s), then DLQ. Heartbeat every 3 s.One poison message can't block a partition; slow LLM calls don't trigger a rebalance.apps/workers/src/queue/consumer.ts
  6. Claim the review. Partial unique index on (PR, head SHA, requester).At-least-once delivery, so duplicates must do no work.apps/workers/src/pipeline/nodes/prepare.ts
  7. Build context. Config from the base commit, snapshot, intent, blast radius (BFS, depth 3), RAG, definitions and call sites.Reading config from base stops a PR from weakening its own rules.analyzers/DependencyGraph.ts · PRDiffSelector.ts · rag/RAGService.ts
  8. Three stages. What changed → how risky → review (quality ∥ security ∥ testing). Every answer goes through Zod with one repair try.Specialists with narrow prompts beat one giant prompt.pipeline/nodes/stages.ts · review-engine/src/assurance/
  9. Dedupe and verify. Merge near-duplicates, verify up to 25 findings. Rejected is removed, uncertain drops one severity.False positives teach developers to ignore the bot.review-engine/src/verify.ts · assurance/findings.ts

6 · Likely questions

Short answers

Is it exactly-once or at-least-once?

At-least-once with idempotent consumers. Exactly-once can't span Kafka, Postgres and GitHub. Dedup happens at three layers: webhook delivery ID, the review claim index, and saving before posting.

What happens if a worker crashes mid-review?

The Kafka offset isn't committed, so the message is redelivered. Every pipeline node also updates a heartbeat on the review row; if it goes quiet for 15 minutes, the recovery sweeper re-queues it, up to 3 times.

How do you stop prompt injection from the PR?

PR text and code go in the user message inside a random tag like <untrusted-3f9a…>, and the system prompt says it is data. The model has no tools and can't approve anything. Policy is read from the base commit. Pass/fail is decided by code.

How do you know the reviews are any good?

The eval harness in apps/workers/evals: PRs with planted bugs run through the real pipeline nodes, scored on precision and recall, before and after the verifier. CI fails if precision or recall drops more than 5 points from the baseline.

The eval also found a real problem: the intent checker repeated real bugs as vague file-level comments. I fixed it and re-measured.

Why does RAG matter if you already have the diff?

The diff hides callers and contracts. In the cents-vs-dollars case the reviewer cited “formatMoney expects a dollar amount” and a call site in checkout.js; neither fact was in the diff. RAG is optional: if embeddings fail, the review runs with less context.

How would you scale to 10,000 PRs a day?

More partitions and worker replicas in the same consumer group, 3 brokers with replication factor 3, retry topics instead of in-handler sleeps, HNSW instead of IVFFlat, cache installation tokens, and debounce rapid pushes to the same PR. The LLM provider's rate limit becomes the real bottleneck, so add a per-tenant token budget.

How would you cut the cost in half?

Skip the testing reviewer when no test files changed (already done), send only commits since the last review on synchronize (already done), use a small model for intent and stage 1 and a strong one only for stage 3 and the verifier, and cache prompts.

How is this different from CodeRabbit?

Same idea, much smaller. What I'd point to is the measured verifier step, blast-radius ranking, and that every gate decision is explainable from policy. I wouldn't claim it is better; it's a project where I owned the whole system end to end.

What would you build next?

Learning from dismissed findings (team memory), cancelling a running review when a new push lands, hybrid search with reranking, and cost-per-review observability.

Did you use AI to write this?

Answer honestly. If you used AI tools, say so, and say what you decided: the outbox, idempotency design, verifier, eval. Then prove it by explaining any file they point at. That's why Saturday is for reading the code.

8 · Weak spots

Say them before they find them

Kafka and workers aren't hosted 24/7.Only the web app is on Vercel. The demo video shows the full flow, and docker compose runs it all.
Single broker, replication factor 1.Fine for a demo; production needs 3 brokers, RF 3, min.insync.replicas=2.
Retries sleep inside the handler.While one message retries, others on that partition wait. Fix: delayed retry topics.
Webhook can exceed 10 s if Kafka is slow.Data is safe in the outbox, but GitHub shows a red delivery. Fix: a hard ~3 s timeout on publish.
Small eval set.13 hand-written cases. Next step: real bug-fix commits from open-source repos.
No cancellation on new push.An outdated review keeps running. Fix: check head SHA between stages and stop early.
